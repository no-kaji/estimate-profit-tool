## スコープ要約

Must 9項目(案件登録、見積/実績レコード分離、スタッフ明細自動計算、法定福利費率マスタ、
収支サマリ集計、請求項目/キャンセルポリシーマスタ、PDF/Excel出力、
経営ボード明細形式でのレコード出力、案件検索・再編集)。Should 2項目、Could 1項目。
詳細は10_product_brief.md参照。月次集計・可視化のダッシュボードはWon't(Power BI担当)。

## 工数感(暫定)

- Solution Architect: データモデル(案件/見積レコード/実績レコード/スタッフ明細/
  請求項目マスタ/料率マスタ)設計、Streamlit+ローカルDB(SQLite等)構成の妥当性検証、
  経営ボード明細スキーマへのマッピング設計(特に「年月」の按分ルール)。小〜中規模。
- Developer: Mustスコープの実装が中心。画面数は月次集計ビューを除いても複数ある
  (案件一覧/見積入力/実績入力/収支サマリ表示/PDF・Excel出力/マスタ管理/
  経営ボード明細レコード出力)ため、初回リリースとしては中規模。
- 全体として「小規模な修正」ではなく、新規業務ツールの初期構築であるため、
  段階的リリース(Mustのみで一旦利用開始→Should以降を追加)を推奨。

## リスク

- **計算ロジックの再現性**: 雛形Excelの数式(社保料率適用、案件収支サマリの按分等)を
  正確に再現する必要がある。Solution Architect/Developerは雛形の数式を突き合わせながら
  実装し、QAは雛形の実例(バックスグループの案件データ)を使った検算を行うこと。
- **経営ボード明細スキーマへのマッピングが未確定**: 収支計算書側の項目(部署/クライアント/
  案件/売上高・売上原価・粗利)と経営ボード明細側の列(統括名称/部門名称/地域区分/
  セグメント/商材/常勤・CA/常勤数/ポジ数/受注状況/ユニット名称/QT/年月)の対応関係、
  特に案件(契約期間)単位のデータを「年月」でどう按分するかが未設計。
  Solution Architectで設計し、判断が難しい場合は人間にエスカレーションすること。
- **法定福利費率の年度改定**: 年度が変わるたびに料率マスタの更新が必要。
  マスタを画面から更新できない場合、運用上の障害になりうる(Mustではないが早期のShouldとして
  検討価値あり)。
- **実行環境の未確定**: Python + Streamlitは依頼者の「意向」であり確定ではない。
  Solution Architectで妥当性(社内配布方法、認証要否、同時アクセス数等)を検証してから確定する。
- **個人情報・取引先情報**: 雛形にはスタッフ氏名・クライアント名等の実データに近い情報が
  含まれる。開発・テストではダミーデータを用い、実データをリポジトリにコミットしない。
